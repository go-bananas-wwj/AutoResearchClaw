## 二、五类根因

1. **契约不一致**（1、5、9、10）：同一规则在提示词与校验器里分别手写，彼此漂移；模型只能靠失败去猜规则。
2. **失败反馈到不了模型**（12）：关卡失败没有强制写成模型可读的结构化产物。
3. **输出预算与回复形态**（2、6、13）：截断与异常回复由各调用点各自处理。
4. **上游旧路径与新架构冲突**（3、7、8）：上游代码假设单文件平铺，并有自己的 LLM 重写修复。
5. **修复粒度与进展度量**（4、11、14、15）：修复粒度过粗，"进展"缺乏可靠定义。

## 三、协作者越界（需框架化）

- 人工恢复约 12 次：每次修框架后由协作者调 API 从阶段 9/10 恢复。框架没有"框架升级后自动重试失败阶段"的机制，无人值守时会停在第一次失败处。
- 因为缓存重放不计次数，每次恢复等于再给一轮完整修复预算，修复上限实际被架空。

## 四、后续迭代建议（按优先级）

1. **框架版本感知的自动恢复**：失败时记录框架版本；版本变化时看门狗自动从失败阶段重试一次，未变化则判真失败。用来取消人工恢复。
2. **缓存回放回归测试**：用 `run_dir/.cache/` 中真实 DeepSeek 回复离线回放整条流水线，不花 API 费用即可提前发现 ①②④ 类框架问题（本次约 10 个问题可这样提前发现）。
3. **契约单一来源**：数据清单、指标输出、数据回执各定义一个 schema，提示词与校验器都由它生成。
4. **关卡不变式测试**：每道关卡失败都必须写出含原因的结构化文件，并出现在修复反馈中。
5. **统一模型调用层**：截断翻倍重试、续写、工具调用标记清理、缓存集中到一处。
